# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Backend build/run tools are the Maven wrapper (no need for a local Maven install):

```
./mvnw compile                              # compile
./mvnw test                                 # run all tests
./mvnw test -Dtest=ClassName#methodName     # run a single test
./mvnw spring-boot:run                      # run the app locally
./mvnw package                              # build the jar
```

On Windows use `mvnw.cmd` instead of `./mvnw`.

The backend requires a MySQL instance (see Database below). Start it with:

```
docker compose up -d      # starts MySQL via compose.yml
```

Frontend (`job-portal-ui/`, separate npm project):

```
npm install
npm run dev        # Vite dev server
npm run build
npm run lint
```

## Architecture

- Spring Boot 4.1.1, Java 21, Maven single-module project. Lombok is available (`@Getter`/`@Setter`/`@RequiredArgsConstructor`, etc.) — prefer it over hand-written boilerplate.
- Base package: `com.backend.jobportal`. Entry point: `JobportalApplication`.
- Feature packages are organized by domain, each with its own subpackages: `controller`, `dto`, `service` (interface, prefixed `I...Service`) and `service.impl` (implementation, suffixed `...ServiceImpl`), `repository` (e.g. `com.backend.jobportal.company.controller`, `company.dto`, `company.service`, `company.service.impl`, `company.repository`). Follow this pattern for new domains rather than layering by type at the top level.
- Entities live in a shared top-level `com.backend.jobportal.entity` package (not per-feature) — e.g. `com.backend.jobportal.entity.Company`, `com.backend.jobportal.entity.Job`, `com.backend.jobportal.entity.JobPortalUser`, `com.backend.jobportal.entity.Role`. New entities should extend `com.backend.jobportal.entity.BaseEntity`, a `@MappedSuperclass` that supplies the `createdAt`/`createdBy`/`updatedAt`/`updatedBy` audit columns via Spring Data JPA auditing (`@CreatedDate`/`@CreatedBy`/`@LastModifiedDate`/`@LastModifiedBy`). Auditing is enabled app-wide via `@EnableJpaAuditing(auditorAwareRef = "auditAwareImpl")` on `JobportalApplication`, backed by `com.backend.jobportal.audit.AuditAwareImpl` (currently a stub `AuditorAware<String>` that always returns `"Anonymous User"` — replace once JWT-derived authentication feeds a real principal into `SecurityContextHolder` on write paths).
- `JobPortalUser` (table `users`) holds `name`, `email` (unique), `passwordHash`, `mobileNumber` (unique), a required `@ManyToOne(fetch = EAGER)` `role` (`Role`, table `roles`, unique `name`), and an optional `@ManyToOne(fetch = LAZY)` `company` (`OnDelete(SET_NULL)`, and `insertable = false, updatable = false` — this FK is not written through the entity, so it must be set some other way, e.g. SQL/a repository update). Repositories: `user.repository.JobPortalUserRepository` (`findByEmail`, `findByEmailOrMobileNumber`) and `user.repository.RoleRepository` (`findRoleByName`).
- `Company` and `Job` have a bidirectional one-to-many/many-to-one relationship: `Company.jobs` is `@OneToMany(mappedBy = "company", cascade = CascadeType.ALL, orphanRemoval = true)`, and `Job.company` is the owning side (`@ManyToOne(fetch = FetchType.LAZY, optional = false)` with `@JoinColumn(name = "company_id")`). The `mappedBy` value must match the field name on the owning side exactly, or the relationship silently fails to load — when adding new relationships, add the owning-side (`@ManyToOne`/`@JoinColumn`) field before or together with the `mappedBy` side.
- Per-domain DTOs (e.g. `CompanyDto`, `JobDto`) are Java `record`s living in `<domain>.dto`, mirroring the entity's fields (a DTO on the "many" side of a relationship, like `CompanyDto.jobs`, holds a `List<JobDto>` rather than the entity list). Service impls map entity → DTO via a private `transformXToDto` helper that calls the record constructor field-by-field; controllers only ever expose DTOs, never entities, in their `ResponseEntity` bodies.
- A `com.backend.jobportal.exception.GlobalExceptionHandler` (`@RestControllerAdvice`) centralizes error handling: generic `Exception`/`NullPointerException` map to a `ErrorResponseDto` (`exception.dto`) with HTTP 500; `MethodArgumentNotValidException` (body `@Valid` failures) and `HandlerMethodValidationException` (method-level `@Validated` failures, e.g. on `@RequestParam`/`@PathVariable`) both map to a field-name → message `Map<String, String>` with HTTP 400.
- There is a `entity-crud-generator` Claude Code skill (`.claude/skills/entity-crud-generator/`) that scaffolds the DTO/Repository/Service/Controller layers for a new entity from templates in `templates/example/` — use it (or match its templates' style) when adding a new domain.
- `com.backend.jobportal.config.web.WebConfig` implements `WebMvcConfigurer` and centralizes MVC configuration:
  - API versioning is configured via `configureApiVersioning`, using a media-type parameter (`application/vnd.backend+json;v=`) with supported versions `1.0`, `2.0`, `3.0`. Controller methods opt into a version via `@GetMapping(version = "1.0")` (etc.) rather than separate URL paths. A request that omits the version parameter/header will not match a versioned mapping — this fails before the handler is reached, which can also make CORS look broken (no `Access-Control-Allow-Origin` header on the failed response) even when CORS itself is configured correctly.
  - All controller paths are prefixed with `/api` via `configurePathMatch`/`addPathPrefix`, so `@RequestMapping` values on controllers (e.g. `/company`) should be written without the `/api` prefix — it is added globally.
  - CORS is configured via `addCorsMappings`, currently allowing `http://localhost:5173` (the local React/Vite dev origin) on `/api/**` with all methods/headers and credentials enabled. Note that Spring Security (see below) applies its own separate CORS config which takes effect first on secured paths.
- `com.backend.jobportal.security` holds the Spring Security setup (`spring-boot-starter-security` + `jjwt`):
  - `PathConfig` defines three named `List<String>` beans consumed by qualifier — `publicPaths` (exact/ant paths, currently just the Swagger/OpenAPI UI routes), `securedPaths` (currently `/api/**`), and `regexPaths` (regex-matched paths, currently `.*public$` so any endpoint ending in `public` is open — this is how `/auth/login/public`, `/auth/register/public`, and `/csrf-token/public` end up unauthenticated without being listed individually). Add new open endpoints to one of these lists rather than editing the filter chain directly.
  - `JobPortalSecurityConfig` wires those beans into the `SecurityFilterChain`: CSRF enabled via `CookieCsrfTokenRepository.withHttpOnlyFalse()` (token delivered as a JS-readable `XSRF-TOKEN` cookie, double-submit pattern) with `CsrfTokenRequestAttributeHandler` (resolves the `CsrfToken` and places it on the request as an attribute keyed by `CsrfToken.class.getName()` — `security.controller.CsrfController`'s `GET /csrf-token/public` just reads that attribute back rather than generating anything itself), its own CORS source (currently duplicating `http://localhost:5173`), regex/public paths permitted, secured paths requiring authentication, form login disabled. `security.filter.JwtTokenValidatorFilter` runs before `BasicAuthenticationFilter`, skipping public/regex paths and otherwise reading the `Authorization` header (strips a fixed 7 characters, so the header must literally start with `Bearer ` — e.g. Postman's "Bearer Token" auth type does this correctly), verifying it with `security.util.JwtUtil` against an HMAC secret (`JWT_SECRET` env var, falling back to a hardcoded default in `constants.ApplicationConstant` — replace before any real deployment), and populating `SecurityContextHolder` from the token's `email`/`roles` claims. HTTP Basic auth (`httpBasic(withDefaults())`) is also still enabled as a fallback auth mechanism. The real authentication path is database-backed: `security.UserPassAuthenticationProvider` (the sole `AuthenticationProvider` bean, injected into `JobPortalSecurityConfig`'s `authenticationManager()` bean) looks up `JobPortalUser` by email via `JobPortalUserRepository` and checks the password with the `PasswordEncoder` (`BCryptPasswordEncoder`) bean also defined in `JobPortalSecurityConfig` — note this creates a real circular dependency (`JobPortalSecurityConfig` → `AuthenticationProvider` → `PasswordEncoder` bean method on `JobPortalSecurityConfig`) if `AuthenticationProvider` is ever wired in via a constructor field instead of a `@Bean`-method parameter. `AuditAwareImpl` remains a stub regardless, since nothing currently pushes the JWT principal into `SecurityContextHolder` before an entity is persisted through the audit-aware write path.
  - Login/registration flow lives in `user.auth` (moved out of the former top-level `auth` package): `user.auth.controller.AuthController` exposes `POST /api/auth/login/public` (takes `LoginRequestDto`, authenticates via `AuthenticationManager`, and on success returns a `LoginResponseDto` with a `UserDto` and a JWT from `JwtUtil.generateJwtToken`, 24h expiry) and `POST /api/auth/register/public` (takes `RegisterRequestDto`, delegates to `user.auth.service.IAuthService`/`AuthServiceImpl`). Send the returned JWT back as the raw `Authorization` header value prefixed with `Bearer ` on subsequent requests to secured paths (the filter unconditionally strips 7 characters, so the prefix is mandatory, not optional).
  - `AuthServiceImpl.apiRegister` builds the `JobPortalUser` (via `BeanUtils.copyProperties` from `RegisterRequestDto`, then hashes the password with `PasswordEncoder`), assigns the `ROLE_JOB_SEEKER` role (looked up via `RoleRepository.findRoleByName`, must already exist in the `roles` table), saves it, and returns a `Map<String,String>` with a `STATUS_SUCCESS` key. Registration *validation* (compromised-password check, duplicate email/mobile) has moved out of this method and into `aspect.RegistrationValidationAspect` (see AOP below) — `apiRegister` itself no longer does that checking.
- `com.backend.jobportal.aspect` holds cross-cutting concerns implemented as AspectJ `@Aspect` beans rather than inline in services/controllers — when adding validation, logging, or post-processing that isn't specific to one method's core logic, prefer a new aspect here over inlining it. `pom.xml` does not declare `spring-boot-starter-aop` explicitly, but AOP support is still fully active: `spring-boot-starter-data-jpa` → `spring-boot-data-jpa` transitively pulls in `spring-aspects`, which pulls in `aspectjweaver` (confirm with `mvn dependency:tree`), and `spring-aop` itself comes in transitively via `spring-boot-starter-security` — together these give Spring Boot's `AopAutoConfiguration` what it needs to auto-activate `@EnableAspectJAutoProxy`-style processing without an explicit AOP starter. If JPA (or its exact dependency shape) is ever removed/changed, re-verify this transitive path still holds, since it's not an explicit, obviously-documented dependency.
  - `LoggingAndPerformanceAspect`: an `@Around` advice on `execution(* com.backend.jobportal..*.*(..))` (i.e. every method in the base package) that logs method name/args on entry and logs execution time on successful return. Being this broad, it fires on every bean method call app-wide, including other aspects' advice.
  - `RegistrationValidationAspect`: a `@Before` advice on `AuthServiceImpl.apiRegister(..)` that performs the registration checks previously inline in that method — compromised-password check via `CompromisedPasswordChecker`, and duplicate email/mobile-number check via `JobPortalUserRepository.findByEmailOrMobileNumber` — and throws `exception.RegistrationValidationException` (a `RuntimeException` carrying a field-name → error-message `Map`) if either fails. `GlobalExceptionHandler.handleRegistrationValidationException` catches it and returns that map as a 400, mirroring the shape used for bean-validation errors elsewhere.
  - `LoginSuccessAspect`: an `@AfterReturning` advice on `AuthController.apiLogin(..)` that logs the authenticated user's name/role on a successful login response, by inspecting the returned `ResponseEntity<LoginResponseDto>`.
  - `ExceptionAuditAspect`: an `@AfterThrowing` advice on the same broad `execution(* com.backend.jobportal..*.*(..))` pointcut that logs any exception propagating out of a method in the base package, independent of whether `GlobalExceptionHandler` also ends up handling it.
  - None of these aspects currently declare `@Order`, so their relative precedence at a shared join point is undefined. This matters concretely for `ExceptionAuditAspect` vs. `RegistrationValidationAspect`: both match `AuthServiceImpl.apiRegister(..)`, and if `RegistrationValidationAspect` ends up positioned outer to `ExceptionAuditAspect` in the resulting interceptor chain, a `RegistrationValidationException` thrown from its `@Before` advice never reaches `ExceptionAuditAspect`'s `@AfterThrowing` (the chain never proceeds far enough to invoke it), even though the exception still correctly reaches `GlobalExceptionHandler`. If audit logging needs to reliably see exceptions thrown by other aspects' advice, `ExceptionAuditAspect` needs an explicit low `@Order` value (high precedence) relative to the aspects it should wrap.
  - Because advice runs based on method signatures/execution pointcuts, a method must be invoked through the Spring proxy (i.e. as a bean, not via `new` or a self-invocation within the same class) for these aspects to apply.
- Data layer: Spring Data JPA against MySQL, run via `compose.yml` (`mysql:latest`, db `jobportal`, root/root, port 3306). `spring.datasource.*` in `application.properties` reads `DATABASE_HOST`/`DATABASE_PORT`/`DATABASE_NAME`/`DATABASE_USERNAME`/`DATABASE_PASSWORD` env vars, defaulting to `localhost:3306/jobportal` with `root`/`root`. H2 (file-based, `AUTO_SERVER=true`) config lines are present but commented out — an earlier setup kept for reference, not currently active.
- Schema and seed data live in `src/main/resources/schema.sql` and `data.sql` (e.g. the `companies` table). `spring.sql.init.mode` is currently commented out in `application.properties`, so these scripts are not auto-run by default — enable that property if schema/data initialization on startup is needed.
- Table columns follow an audit convention: `created_at`, `created_by`, `updated_at`, `updated_by` (see `companies` in `schema.sql`) — follow this pattern for new tables/entities.
- `spring-boot-devtools` is enabled for auto-restart during development.
- Frontend (`job-portal-ui/`) is a separate Vite + React 19 project (not a Maven module): Redux Toolkit for state, React Router 7, Tailwind 4, Axios for API calls, Stripe (`@stripe/react-stripe-js`) for payments. Dev server runs on `localhost:5173`, matching the CORS origin configured in `WebConfig`.
